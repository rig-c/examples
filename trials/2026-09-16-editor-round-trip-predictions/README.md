# 2026-09-16 editor-round-trip-predictions: does the Spine editor keep what rig-c emits?

## Question

When a skeleton built by `@rig-c/core` 0.21.0 is imported into the Spine
editor 4.3.26 and exported again with the editor's default JSON settings, does
each construct the compiler emits come back? The question covers the 36
constructs that no earlier editor round trip had carried: bounding box and
clipping attachments, an unweighted mesh, transform constraints, a time-driven
slider, shear and draw-order timelines, non-default path modes, and others.
Before the editor ran, a prediction was written for each construct. The
measurement checks every prediction.

```bash
# Run from this directory, RIGC_ROOT = a rig-c/core checkout at d8485ea, with a licensed Spine editor installed.
RIGC_ROOT=<core checkout> ./run-all.sh        # all eight rigs; output kept as out/run-all.log
bun read.ts --all --out out                   # the 72 verdicts
```

For each rig, `run-all.sh` runs these four commands, in this order:

```bash
bun rigs/<rig>/r6_make_plates.ts
bun "$RIGC_ROOT/cli.ts" build --rig rigs/<rig>/rig.json --motion rigs/<rig>/motion.json --out out/<rig>/build --copy-images   # --pack for `packed`
bun "$RIGC_ROOT/tools/editor_roundtrip.ts" --build out/<rig>/build --out out/<rig>/roundtrip --name <rig> --fps 12 --timeout 600
bun read.ts --rig <rig> --build out/<rig>/build --export out/<rig>/roundtrip/export
```

The harness has six steps: import (JSON to project), export (project to JSON
with `-e json`, the editor's default settings), `validate --profile spine` on
the export, `diff` of the export against the build, rendering both at 12 fps and
running `check` of the export against the build's frames, and a summary of what
the editor rewrote. No outer timeout wraps the editor calls. The harness bounds
each one itself (`--timeout 600`), and an outer bound would kill it before it
writes `roundtrip.log`.

`bun read.ts --all` exits 1 whenever a row is not CONFIRMED. It also prints
`run-all.log NOT RUN`, because it treats `out/run-all.log` as a rig directory.
That line is not a row.

## Measurement

**How a row is judged** (fixed before the run, in `predictions.json` and
`read.ts`). Each row names a probe, which is a path into the skeleton. It also
lists the competing hypotheses for what the export will contain, and which one
the table predicts. `read.ts` resolves the probe on the build and on the export,
then keeps every hypothesis whose expected observation matches:

| Hypotheses that survive | Verdict |
| --- | --- |
| exactly one, and it is the predicted one | CONFIRMED |
| exactly one, and it is another | REFUTED, naming what came back |
| more than one | AMBIGUOUS |
| none | REFUTED, "no hypothesis on the table predicted this observation" |

The table has 72 rows. By basis, 40 rest on an official Spine page, 14 are
inferred from an earlier measurement, and 18 have no basis at all. Twelve of
the rows are fixed-point controls.

**Bar, stated before the run:** every construct the table carries comes back.
A REFUTED row counts against the bar only if what came back is a loss.

**The first six rows: nonessential data is on.** The five `doc` rows predicted
`dropped` from the documented nonessential list (the JSON-format and Export
pages, quoted in rig-c/core's `docs/AUTHORING.md` §10.5). That list says these
fields are written only when the *Nonessential data* box is checked. Every
field came back. Each export also carries `"audio": "./audio"`, a field the
build never wrote. Together these show that the harness's bare `-e json` export
runs with nonessential data **on**. The Spine command-line page says a bare
format name exports "using default settings". Neither that page nor the Export
page says whether those defaults include nonessential data, so the answer here
was measured and is not documented anywhere. rig-c wrote correct data and got
it back, so this is not a defect.

On the same rig, FI-08 is CONFIRMED: the five-vertex mesh's `hull` came back as
4 and was not recomputed. `out/fields/roundtrip/roundtrip.log` has no import
warning. So the degradation of rig-c/core#368 did not return, where the editor
recomputed the hull and dropped the edges of an authored mesh.

**PA-08.** Compare the key in the build with the key in the export:

```
build  key 0: {"time":0,"mixRotate":0.5625,"mixX":0.4375,"mixY":0.21875,"curve":[0.25,0.5625,0.75,0.75,0.25,0.4375,0.75,0.5,0.25,0.21875,0.75,0.28125]}
export key 0: {         "mixRotate":0.5625,"mixX":0.4375,"mixY":0.21875,"curve":[0.25,0.5625,0.75,0.75,0.25,0.4375,0.75,0.5,0.25,0.21875,0.75,0.28125]}
```

The parser treats a missing `time` as 0, so nothing was lost. The table lacked
a `without: ["time"]` hypothesis. All four mechanisms predicted in
`pa08-mechanism-prediction.txt` (P1 to P4) were wrong. The reader reported "no
hypothesis on the table predicted this observation" instead of matching the
nearest hypothesis, which is how it is meant to behave. Any value row that
probes a whole key object has to allow for an elided `time: 0`.

### The unpredicted finding: the editor rewrites a path's `lengths`

There is one more difference between build and export that the prediction
table had no row for. The comparison treats numbers as equal within 1e-9 and
ignores fields that one side omits because they equal their default. With
those rules, here is every remaining difference:

| Rig | Differences |
| --- | --- |
| seven rigs | the three header fields the editor stamps: `skeleton.audio`, `skeleton.hash`, `skeleton.spine` (`4.3.13` → `4.3.26`) |
| `pathmodes` | those three, plus the four entries of the closed path attachment's `lengths` |

```
build  lengths: [153.780555, 307.56111, 461.341665, 615.122221]
export lengths: [152.7006,   305.4012,  458.1019,   610.8025]
ratio         : 0.992977 on every entry (rig-c is about 0.70% high)
```

The `lengths` are the only semantic difference on the one rig whose frames
moved: 0 of 25 frames are byte-identical, mean MAE 4.9612, worst 7.8243. On
the other seven rigs, every frame is byte-identical. `diff` reads 40 / 40
perfect because it does not compare a path's `lengths`. `A33` checks only that
`lengths` increases, and both arrays do. The gate was green, `diff` was
perfect, and the picture still moved.

**Mechanism, reproduced.** rig-c/core at `d8485ea` measures each curve with a
chord sum at `PATH_LENGTH_SAMPLES = 64`. Running the same chord sum over the
same control points at other sample counts gives cumulative lengths for curve 0
and curve 3. This was recomputed for this write-up from
`out/pathmodes/build/skeleton.json`:

| Samples per curve | `lengths[0]` | `lengths[3]` |
| ---: | ---: | ---: |
| 2 | 150.120294 | 600.481174 |
| 3 | 151.940857 | 607.763428 |
| **4** | **152.700630** | **610.802520** |
| 5 | 153.077905 | 612.311621 |
| 8 | 153.503931 | 614.015725 |
| 64 (what rig-c wrote) | 153.780555 | 615.122221 |
| 4096 (close to the true arc length) | 153.784987 | 615.139948 |

Four samples per curve reproduces every digit the editor prints. That matches
the four-step forward difference that spine-core's `PathConstraint` uses when
it re-measures a `constantSpeed` path. The original results also report that
an inflated `.spine` project holds rig-c's values and not the editor's, which
places the substitution at **export**. Under `spacingMode: proportional`, a
total 0.7% long moves every constrained bone. This is a rig-c defect, not an
editor loss: rig-c's number is the better arc length and the wrong one for the
format.

### Other observations

These are not rows, and they come from the original results.

- In rig-c/core at `d8485ea`, the summary step (step 6) of
  `tools/editor_roundtrip.ts` counts constraints from the top-level arrays used
  before 4.3 (`ik`, `transform`, `path`, `physics`). 4.3 puts all constraints in
  one `constraints[]` array, so that summary reads 0 → 0 on every trip. The
  `diff` in step 4 does read `constraints` correctly.
- A `--pack` build writes `"images": "../../rigs/packed/parts/"`, which points
  outside the build. `PK-01` and `PK-02` were CONFIRMED only because the loose
  parts were still in place. This run does not show the failure.

## Verdict

**PASS** — of the 72 rows, 65 are CONFIRMED, 7 REFUTED and 0 AMBIGUOUS. None of
the 7 refutations is a construct the editor lost: six had a wrong premise, the
fields came back unchanged because the default CLI export writes nonessential
data, and one row was built wrong (`"time": 0` elided as a default, every
value intact). So all 36 previously unmeasured constructs survived the Spine
4.3.26 import → export round trip. One finding fell outside the table: the
editor recomputes a path attachment's `lengths` at export with 4 samples per
curve, where rig-c 0.21.0 wrote 64 (153.780555 → 152.7006 on the first entry,
0.70% low on every entry). That moved the `pathmodes` drawing by mean MAE
4.9612 while the gate stayed green and `diff` read 40 / 40. It is a defect in
rig-c's number, not a loss in the editor.

## Rejected alternatives

- **Re-running the gallery rigs as a regression.** These rigs had already
  round-tripped twice and their emitted surface had not moved. A round trip
  yields new information only when the surface grows, so the editor time went
  to the 36 constructs nothing had carried.
- **One rig carrying every construct.** A single import failure would take
  every measurement down with it, as a four-skin rig did in rig-c/core#541. The
  eight rigs fail independently.
- **One rig per construct.** Several constructs are reachable only together: a
  `transform` timeline needs a transform constraint, and a path mode needs a
  path attachment and a path constraint. One rig per field would have meant
  about forty rigs and forty editor runs. The constructs were grouped by what
  has to coexist, with a fixed-point control in each rig.
- **Rows that compare whole timeline arrays.** rig-c/core#535 measured the
  editor rewriting curve encodings on 196 of 200 keys, so every such row would
  be REFUTED for a reason unrelated to its question. Survival and value are
  separate rows, and the value rows probe one key. PA-08 shows the cost of
  probing a whole key.
- **Writing the six `dropped` rows as observations instead of predictions.**
  If the editor kept a field, the row had to be able to say REFUTED. It did,
  six times.
- **Wrapping the editor calls in an outer timeout.** The harness bounds each
  call itself and reports a hang as a hang. An outer bound would kill it before
  `roundtrip.log` is written.
- **Calling the verdict PARTIAL because of the `lengths` drift.** The bar set
  before the run was the prediction table. The drift is outside the table and
  is not a construct the editor dropped. It is rig-c's value disagreeing with
  the model that the editor and the runtime share. It is stated in full in the
  verdict instead of being folded into the bar after the result was known. A
  reader who counts every emitted *value* rather than every *construct* would
  call this run PARTIAL, and the figures above support that reading too.

## Limits

- **The pins are old.** The run was rig-c/core 0.21.0 at `d8485ea` against
  Spine editor 4.3.26 on 2026-09-16. It says nothing about any later core or
  editor release, including whether a later core still writes 64-sample
  `lengths`. A re-run on a current `@rig-c/core` is a **new trial** with its
  own date, not an update to this one.
- **Population:** eight generated rigs, one editor session, one machine. Each
  construct is carried once, with the values the rigs chose.
- **Six constructs were not covered**, as the preparation stated: several
  skins and per-skin bone or constraint lists, bone `skin: true`, clipping
  `inverse`, event `audio` / `volume` / `balance`, and `--atlas-in`. Some
  timeline kinds (`bone.inherit`, `slot.rgb` / `alpha` / `rgba2` / `rgb2`,
  `sequence`, `drawOrderFolder`) were also not covered, because the compiler
  at that commit could not emit them. Multi-skin fixtures were tripped
  in separate runs after midnight (log times 00:04 to 01:38 on 2026-09-17).
  They are not part of this trial.
- **Only the CLI's default export was measured**, which has nonessential data
  on. An export with nonessential data off would need an export-settings file,
  and none was made. The six `dropped` predictions are untested against that
  export.
- **The plates are placeholders.** No claim about appearance, seams or
  blending comes from them. The MAE and frame-hash figures say only whether
  the build and the export draw the same, not whether either looks right.
- **Some figures are not re-derived here.** The import-versus-export placement
  of the `lengths` substitution and the step-6 constraint blindness come from
  the original results. They rest on the withheld `.spine` files and on the
  harness source at `d8485ea`, and were not re-run for this write-up. The
  sample-count table, the semantic diff, the 72 verdicts and the frame hashes
  were re-run.
- **Nothing was judged by eye.**
